# C. AIプロダクト パターン

> 2026年11月時点の前提で書いている。モデル性能・推論コスト・競合の状況は変化が速いため、半年ごとを目安に見直す。

カードの項目：症状 / 構造（なぜ起きるか）/ 確認 / 反証 / 定石 / 落とし穴 / 元概念

### C1. ラッパーの脆さ
- 症状：基盤モデルの上に薄い機能を乗せた製品が、モデル提供者の機能追加や汎用AIアシスタントの性能向上で価値を失う
- 構造：差別化がモデルの能力に依存していると、その能力はモデル側の進化で誰でも使えるようになる
- 確認：最新の汎用AIで同じタスクをしたときに、自社製品との差がどこにあるか。差の源泉がプロンプトだけか、データ・ワークフロー・統合か
- 反証：独自データ、業務への深い統合、規制対応など、モデルの進化で代替されない要素が価値の中心にある
- 定石：モデルの進化を追い風にできる設計にする（モデルが良くなるほど自社製品も良くなる）。価値の源泉をワークフロー、データ、配置に移す
- 落とし穴：モデルの弱点を補う機能に投資し、次のモデルで不要になる
- 元概念：アドバンテージの源泉、デコンストラクション

### C2. 限界費用の再浮上
- 症状：AI機能の利用が増えるほど粗利率が下がる。ヘビーユーザーが赤字になる
- 構造：従来のSaaSは限界費用がほぼゼロだったが、AI機能は推論ごとにコストが発生する。定額課金と組み合わせると利用が多いほど損をする
- 確認：顧客別・機能別の推論コストと売上。利用量の分布（一部のヘビーユーザーに集中しているか）
- 反証：推論コストが売上に対して十分小さく、モデル価格の下落で今後さらに下がる見込みが高い
- 定石：利用量に連動した課金や上限設定。タスクに応じたモデルの使い分け、キャッシュなどによるコスト最適化
- 落とし穴：コストを気にして機能を制限しすぎ、体験の価値を落とす。モデル価格の下落を過大に見込む
- 元概念：コストビヘイビア、ユニットエコノミクス

### C3. デモと本番の溝
- 症状：PoCやデモの評価は高いのに、本番導入・全社展開に進まない
- 構造：デモで見せる成功ケースと、本番で求められる精度・一貫性・例外処理・説明責任の水準に大きな差がある。最後の数%の精度に最も工数がかかる
- 確認：PoCから本番への移行率と、止まった理由。本番で求められる精度とその計測方法が顧客と合意されているか
- 反証：本番移行は進んでいて、止まっている理由が予算や社内調整など非技術的なもの
- 定石：完全自動化ではなく、人が確認する前提のワークフローで先に本番に入る。評価基準を顧客と最初に合意する
- 落とし穴：デモの好評を需要の証拠と誤認して、販売体制を先に拡大する
- 元概念：組織学習、タイムベース競争

### C4. 労働代替による自己カニバリ
- 症状：AIで顧客の業務が効率化されるほど、顧客が必要とするシート数が減り、既存の売上が縮む
- 構造：人数に比例する課金モデルと、人の作業を減らすAIの価値が真っ向から矛盾する
- 確認：AI機能を深く使っている顧客の、シート数の推移
- 反証：AIによって利用者が増える（新しい職種が使い始める）効果のほうが大きい
- 定石：成果やタスク量に連動した課金に移行する。シートではなく「デジタルな労働力」として価格を付ける
- 落とし穴：既存売上を守るためにAI機能の価値を抑え、AIネイティブな競合に先を越される（A3に連鎖）
- 元概念：イノベーションのジレンマ、価値ベース価格設定

### C5. データフライホイールの幻想
- 症状：「利用データが溜まれば精度が上がって勝てる」が戦略の前提になっているが、実際には差が広がっていない
- 構造：データが価値になるのは、利用からフィードバックを得て、それが製品改善に戻る仕組みが設計されているときだけ。さらに、汎用モデルの進化が独自データの優位を相殺することがある
- 確認：データ量の増加と、品質指標の改善に相関があるか。フィードバックを製品に戻す仕組みが実際に動いているか
- 反証：独自データで明確に品質差が出ていて、その差が時間とともに広がっている
- 定石：フィードバックループを明示的に設計する（利用→評価→改善）。データの量より、他社が取れない種類のデータに集中する
- 落とし穴：データの蓄積そのものを目的化して、価値の検証を後回しにする
- 元概念：エクスペリエンスカーブ、組織学習

### C6. ワークフローへの埋め込みが堀（勝ちパターン）
- 症状：AIの精度そのものでは競合と大差ないが、顧客の業務の流れの中に入り込んでいて置き換えにくい
- 構造：モデルの能力は均質化しやすい。差が残るのは、どの業務のどの瞬間に、どの文脈（データ、権限、前後の作業）を持って介入できるか
- 確認：利用が業務の流れの中で自然に発生しているか（わざわざ開いて使うツールか）。業務データや他システムとの連携の深さ
- 反証：利用者が明示的に開いて使うだけで、業務上の文脈を持っていない
- 定石：単体ツールではなく、既存の業務システムや作業の流れの中に配置する。文脈データへのアクセスを確保する
- 落とし穴：埋め込み先のプラットフォームに依存しすぎる（B3に連鎖）
- 元概念：スイッチングコスト、System of Record
